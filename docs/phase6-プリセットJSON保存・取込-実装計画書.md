# Phase 6: プリセットのJSON保存・取込 実装計画書（v0.3.0）

対象: [rename-date開発計画書.md](./rename-date開発計画書.md) の画面・サービス要件、ロードマップ、配布・テスト方針。[Phase 5](./phase5-期間表記対応-実装計画書.md) で導入した期間用プリセット管理と、[Phase 4](./phase4-配布パッケージング-実装計画書.md) の配布手順を引き継ぐ。

## 目的

入力パターン（正規表現）と単日・期間の出力テンプレートを、利用者が指定した場所にJSONで保存し、別の環境などで取り込めるようにする。既存の内部設定やファイル名変換の挙動は維持し、本改修を含むアプリのバージョンを `v0.3.0` に上げる。

## 要件

### A. 保存・取込の単位とファイル形式

- 入力パターン、単日出力テンプレート、期間出力テンプレートの3種類をそれぞれ個別に扱う。保存対象は選択中の項目だけではなく、指定した種類の全件とする。
- 既存の内部保存と同じUTF-8（BOMなし）のJSON配列で保存する。取込時はWindowsのエディタ等で付与されたBOM付きUTF-8（`utf-8-sig`）も読み込みを許容し、内部設定への保存時は常にUTF-8（BOMなし）で書き出す。配列は空にできず、各要素は次のキーを持つ文字列値のオブジェクトとする。

  | 対象 | キー | 保存ダイアログの既定ファイル名 |
  |---|---|---|
  | 入力パターン | `name`, `pattern` | `patterns.json` |
  | 単日出力テンプレート | `name`, `template` | `output_templates.json` |
  | 期間出力テンプレート | `name`, `template` | `range_output_templates.json` |

- 配列の並び順、日本語の名前、正規表現のバックスラッシュ、テンプレート本文を保存→取込で保持する。テンプレートの単日・期間は取込メニューで指定し、選んだ種類の検証に通らないデータは拒否する。
- 稼働中の内部設定ディレクトリ（通常実行時は `%APPDATA%\rename-date\config`、各サービスの `base_dir`）配下の3ファイルは、保存先・取込元として直接指定できない。他の環境からコピーした同じ形式のJSONは取り込める。内部設定のファイル名・スキーマは変更せず、移行処理を設けない。

### B. 取込と上書きのルール

- 取込は**追加のみ**。既存一覧の末尾にJSON配列の順序で追加し、既存項目の相対順も保つ。取込後も、変換時は期間パターンが先に適用され、同種内では表示順を保つ。
- 同じ種類の中で、取込ファイル内または既存一覧と同じ名前が一つでもあれば、全件を拒否する。内容が同じ場合も拒否する。名前の比較は現在と同じ完全一致（大小文字を区別）とし、別の種類との同名は許可する。既定プリセットも例外にしないため、取込先に同名の既定プリセットがあるときは、JSONのコピーから重複項目を除くか、名前を変更してから取り込む。重複エラー時は、衝突したプリセット名をダイアログに明示する。
- 既存の正規表現検証（3グループは単日、4〜6グループは期間）および単日・期間それぞれのテンプレート検証を適用する。不正なJSON、項目の形式不一致、同名、読込・保存エラーは利用者へ通知する。不正データを既定値に置き換えない。
- 取込元は読み取り専用で扱う。取込データと追加後の一覧をすべて検証してから、対象の内部設定ファイルを一度だけ更新する。失敗やキャンセルで、取込元・内部設定・一覧・プレビューを変更しない。
- JSON保存で既存の外部ファイルを指定した場合は上書き確認を行う。OS標準の上書き確認とは二重にせず、アプリ側で「内部設定3ファイルの拒否判定 → 既存ファイルの上書き確認 → 書出し」の順に処理する。書込みは保存先と同じディレクトリの一時ファイルに完了してから置換し、確認の取消や書込失敗で既存ファイルを壊さない。

### C. 画面とプレビュー

- メニューバーに「プリセット」を追加し、その配下に「入力パターン」「単日出力テンプレート」「期間出力テンプレート」の3つのサブメニューを置き、各サブメニュー内に「JSONに保存...」「JSONから取込...」を配置する（全メニューで `tearoff=False` を指定する）。既存の編集ボタンや最小ウィンドウサイズ（`700x450`）は変更しない。
- 保存・取込にはJSON用のファイルダイアログを使用する。キャンセル時は何もしない。走査・一括変換・Undoの処理中は取込を開始せず、利用者に通知する。
- 取込成功後は対象の一覧だけ更新し、選択中のパターンとテンプレートを名前で維持する。未選択の場合もその状態を維持し、追加項目は自動選択しない。
- 取込成功後は古いプレビューを破棄し（走査結果0件の「対象がありません」表示にはせず空状態に戻す）、ステータス欄と完了通知で再プレビューを案内する。新しいプレビューができるまで古い結果で一括変換できないようにし、Undo履歴は保持する。JSON保存では選択やプレビューを変更しない。

## タスク

### 1. Services：JSON入出力

- [x] [PatternService](../src/rename_date/services/pattern_service.py) と [OutputTemplateService](../src/rename_date/services/output_template_service.py) に任意のパスへの書出し・取込を追加する。期間用サービスは既存のサブクラス構造を利用し、期間用の検証を維持する。書出しは `encoding="utf-8"`（BOMなし）、取込は `encoding="utf-8-sig"` で読み込む。
- [x] 既存のJSON変換・検証・一時ファイルによる保存処理を再利用する。取込のために項目ごとの `upsert()` は呼ばず、取込データと追加後の一覧を検証してから1回保存する。Services層に `tkinter` や新しい依存パッケージを追加しない。
- [x] [validation.py](../src/rename_date/services/validation.py) の既存英語メッセージおよび既存テストとの互換性を維持しつつ、プリセット入出力用の構造化エラー（理由種別・該当項目名・配列位置・詳細を持つ `ValueError` サブクラス等）をServices層に用意し、重複名や検証失敗の対象項目を呼び出し元へ伝えられるようにする。
- [x] JSON入出力では、外部ファイルも現在の内部設定も、失敗を呼び出し元へ返す読込経路を使う。初回起動や破損した内部設定から既定値を復元する既存の `load()` の挙動は変えない。
- [x] 内部設定の3ファイル名を [config.py](../src/rename_date/config.py) 等の共通定数に集約し、JSON入出力の前に指定パスが `self.base_dir` 配下の内部設定3ファイルのいずれかでないことを確認する。未作成ファイルやシンボリックリンク、Windowsの大文字・小文字の違い、相対パスを含めて安全に判定できるよう、双方に `Path.resolve(strict=False)` と `os.path.normcase()` を適用して比較する。

### 2. Views・Controller：操作の接続

- [ ] [MainWindow](../src/rename_date/views/main_window.py) に「プリセット」メニュー（3サブメニュー×保存・取込、`tearoff=False`）と保存・取込のファイルダイアログを追加する。保存ダイアログは `defaultextension=".json"`、`confirmoverwrite=False` とし、内部設定3ファイルの拒否判定を行った後に既存ファイルの上書き確認（`messagebox.askyesno`）を行ってから書き出す。
- [ ] [AppController](../src/rename_date/controllers/app_controller.py) で種類に応じたサービスへ処理を渡す。取込はダイアログを開く前に処理中かを確認する。Services層の構造化エラーおよびI/Oエラーを日本語のエラーダイアログへ整形して通知し、可能なら該当するファイル・項目名（重複時は衝突したプリセット名）・理由を示す。成功時は保存先または取込件数（取込時は再プレビュー案内を含む）を通知する。
- [ ] [ConfigFrame](../src/rename_date/views/config_frame.py) の一覧更新で、取込時に限り既存の選択を名前で復元する。選択中名称から復元インデックスを解決する処理を純粋関数（例: `resolve_selected_indices`）として切り出し、複数選択・未選択の維持を単体テスト可能にする。起動時と従来の編集・削除操作の選択挙動は変えない。
- [ ] [PreviewFrame](../src/rename_date/views/preview_frame.py) に `clear()` を追加し、取込成功時のみプレビュー表示（空状態へのリセット）・件数・ステータスと、Controllerが保持する実行候補および再スキャン用の条件をクリアする。また、再スキャン条件が `None` の状態でUndoが完了・キャンセルされた場合も [_on_undo_complete](../src/rename_date/controllers/app_controller.py) / [_rescan_after_operation](../src/rename_date/controllers/app_controller.py) でステータスと進捗を適切に更新し、古い条件のプレビューが復活しないこととステータスが固まらないことを確認する。
